# Module Specification: Member Registration

**Status**: Deferred  
**Date**: 2026-07-27  
**Context**: 顯恩堂系統 / EFCC Church Management System

> **Deferral decision (2026-07-28):** Web-app registration is outside the first
> release. Member creation continues through the existing manual Users-sheet
> process. The deployed app exposes no Register view/button and no
> browser-callable registration mutation. No `Registration_Requests` sheet or
> setup script is introduced. The remaining sections below are retained as
> historical candidate behavior only and are not implementation requirements.

---

## 1. Purpose

Allow church administrators to register new members into the system, and allow the spreadsheet to auto-generate credentials when rows are added manually. Members receive a username, a 4-digit PIN, and a unique identifier (User_ID / QR code).

---

## 2. Data Model (Users Sheet)

| Column | Example | Generated by | Notes |
| --- | --- | --- | --- |
| User_ID | `GC-A1B2-C3D4` | `registerNewMember` or `onEdit` | "GC-" + two random hex segments. Also used as QR_Code_String. |
| Name | `John Doe` | User input | Free text, trimmed. |
| Username | `johndoe` | `registerNewMember` | Lowercased name with spaces removed. Appends `1`, `2`, ... on collision. |
| PIN_Code | `1234` | `registerNewMember` or `onEdit` | Random 1000–9999. |
| Phone | `+852 1234 5678` | User input | Free text, trimmed. |
| Role | `Member` | `registerNewMember` | Always "Member" by default. |
| Status | `Active` | `registerNewMember` | Always "Active" by default. |
| QR_Code_String | `GC-A1B2-C3D4` | `registerNewMember` or `onEdit` | Same value as User_ID. |

## 3. Registration Flow (registerNewMember)

**Trigger**: Admin calls `registerNewMember(name, phone)` from the web app UI.

1. Validate inputs: name is required, phone is optional.
2. Generate User_ID: `"GC-" + hex1 + "-" + hex2` where each hex fragment is a random value between `0x1000` and `0xFFFF`.
3. Generate PIN: random integer between 1000 and 9999.
4. Generate Username:
   - Base: `name` lowercased, whitespace removed.
   - Check against all existing username values in the Users sheet.
   - If collision exists, append incrementing integers (`johndoe`, `johndoe1`, `johndoe2`, ...) until unique.
5. Populate a new row: fill columns by name lookup. Columns not found in the sheet are silently skipped.
6. Append the row to the Users sheet via `appendRow`.
7. Return `{ Username, PIN, Name }` to the caller.

### Code Location

`function registerNewMember(name, phone)` at line 369 of `程式碼.js`.

### Acceptance Criteria

- [ ] New row is appended to the Users sheet with all known columns populated.
- [ ] User_ID is in format `GC-XXXX-XXXX` (uppercase hex, 4 chars per segment).
- [ ] PIN is a 4-digit number between 1000–9999.
- [ ] Username is unique — if the display name collides, a counter suffix is appended.
- [ ] Default Role = "Member", Status = "Active".
- [ ] QR_Code_String equals User_ID.
- [ ] Unknown/missing columns in the sheet header skip that value silently (no crash).

## 4. Auto-ID onEdit Trigger

**Trigger**: Google Sheets `onEdit` event fires when any cell in the spreadsheet is edited.

**Behavior**:

1. Ignore edits on sheets other than "Users".
2. Ignore edits on the header row (row 1).
3. For each edited row: if the Name cell has a value AND the User_ID cell is empty, auto-generate:
   - User_ID (`GC-XXXX-XXXX`)
   - PIN (random 1000–9999)
   - QR_Code_String (= User_ID)
4. Write values directly to the edited row (no append).

### Code Location

`function onEdit(e)` at line 418 of `程式碼.js`.

### Acceptance Criteria

- [ ] Non-Users sheet edits are ignored.
- [ ] Header row edits are ignored.
- [ ] Rows with an existing User_ID are untouched (idempotent).
- [ ] Rows without a Name value are untouched.
- [ ] Generated ID follows the `GC-XXXX-XXXX` format.
- [ ] PIN and QR_Code_String are written alongside User_ID in the same row.

## 5. Credential Update — Spreadsheet Administration Only

Username and PIN changes are not available through the deployed web app. An
authorized spreadsheet administrator changes those fields directly in the
`Users` sheet. There is no browser-callable credential-update RPC and no Profile
credential form.

Spreadsheet administration must preserve the existing rules: username remains
unique and normalized; PIN remains exactly four numeric digits. Because the
custom Session token is derived from the stored PIN, changing the PIN invalidates
the prior token. On its next server validation, the stable App Document shows
Login with `AUTH_REQUIRED`; it must not render a blank document.

### Acceptance Criteria

- [ ] No browser-callable function updates Username or PIN.
- [ ] Profile exposes no Username/PIN edit form.
- [ ] A spreadsheet PIN change causes the old Session token to return
      `AUTH_REQUIRED` and visibly show Login without replacing the App Document.

## 6. Edge Cases & Error Handling

| Scenario | Behavior |
| --- | --- |
| Name is empty | Currently not validated at server level — caller should validate client-side. |
| Phone contains non-digit characters | Accepted as-is (free text field). |
| Users sheet is missing | `registerNewMember` will throw → caught by `withFailureHandler`. |
| onEdit fires on a row with Name but no ID (manual entry) | ID, PIN, QR auto-generated — allows admin to add members by just typing a name in the sheet. |
| Spreadsheet administrator changes PIN | Existing custom Session token becomes invalid; user logs in again. |
