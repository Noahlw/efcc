# PRG-04 (#200) — Program Leader & delegation slice — acceptance trace

> This trace is written **before** implementation (ADR-0012 headless gate). Each
> acceptance criterion is listed with its assertion method via observable
> worker-contract state. Verification results are appended at the end.

Basis: ADR-0006 (Program Leader model — scoped relationship, never a global
Role; grant/revoke is Admin/Staff only) + ticket #200 acceptance criteria.

## 1. RPC contract — Leader assignment (delegation)

| # | Criterion | Assertion method |
| --- | --- | --- |
| DLG-1 | `POST /api/v1/programs/:id/leaders` `{ user_id }` assigns an active leader when the actor has `program.leader.assign` for that exact program | Staff actor → `201 { requestId, data: { leader } }` with `revoked_at: null`; a `PROGRAM_LEADER_GRANT` audit row exists (actor, target user, timestamp, correlation_id) |
| DLG-2 | Assignment is idempotent: re-assigning an already-active pair succeeds without creating a duplicate row | second `POST` with same pair → `200` (or `201` with same row), still exactly **one** active row; audit `DUPLICATE` outcome row appended |
| DLG-3 | Active assignment pairs cannot be duplicated | partial unique index `program_leaders_active_idx` enforced; concurrent double-insert collapses to one row; no two rows with `revoked_at IS NULL` for the same pair ever |
| DLG-4 | Assigning an already-revoked pair reactivates it | assign → revoke → assign again → `revoked_at` becomes `null`, single active row again, history rows preserved |
| DLG-5 | Unknown target user → validation error, no row, no grant audit | `POST { user_id: "ghost" }` → `422`; zero `program_leaders` rows; zero `PROGRAM_LEADER_GRANT` audits |
| DLG-6 | Unknown program → `403 FORBIDDEN` (unknown scopes are indistinguishable from denied, no existence leak) | `POST /api/v1/programs/nope/leaders` → `403`, no audit rows |
| DLG-7 | Member (global Role `Member`) cannot assign | Member actor → `403 FORBIDDEN`, no audit rows |
| DLG-8 | A scoped Program Leader cannot assign — leadership grants only operational capabilities, never `program.leader.assign` | grant leader on program P (insert `program_leaders`), actor = that leader, `POST /api/v1/programs/P/leaders` → `403` |
| DLG-9 | A caller cannot self-grant | `POST { user_id: <actor's own id> }` → `403`, no audit rows |
| DLG-10 | A caller cannot grant beyond their authority: assigning into a program they cannot manage is denied even if they lead a different program | leader of program A, `POST /api/v1/programs/B/leaders` → `403` (A ≠ B) |

## 2. RPC contract — Leader revocation

| # | Criterion | Assertion method |
| --- | --- | --- |
| DLG-11 | `POST /api/v1/programs/:id/leaders/:userId/revoke` revokes an active leader (soft revoke) | Staff actor → `200 { requestId, data: { leader } }` with `revoked_at` set; `PROGRAM_LEADER_REVOKE` audit row (actor, target, timestamp, correlation_id); the revoked leader's `program.manage` grant is gone → their subsequent `POST /schedule-rules` on that program → `403` |
| DLG-12 | Revoking a non-leader → `404 NOT_FOUND` | revoke member who was never a leader → `404`; revoke twice → second `404` (or idempotent `200` — see DLG-13) |
| DLG-13 | Revocation is idempotent/explicit: revoking an already-revoked pair is a no-op success | second revoke → `200` with unchanged row, no second `PROGRAM_LEADER_REVOKE` audit |
| DLG-14 | Member cannot revoke; scoped Program Leader cannot revoke | Member → `403`; leader on P revoking another leader on P → `403` |
| DLG-15 | Revocation is permanent and queryable | after revoke, the row persists in `program_leaders` with `revoked_by` + `revoked_at`; audit row immutable (UPDATE/DELETE rejected) |

## 3. RPC contract — Leader listing

| # | Criterion | Assertion method |
| --- | --- | --- |
| DLG-16 | `GET /api/v1/programs/:id/leaders` lists active leaders for a program | Staff/Admin → `200 { requestId, data: { leaders: [...] } }` — active only, `revoked_at IS NULL` |

| DLG-18 | Member → `403`; leader of a different program → `403` | Member → `403`; leader on A requesting B's leaders → `403` |

## 4. Authorization model (capability + authorizer)

| # | Criterion | Assertion method |
| --- | --- | --- |
| AUTH-1 | `program.leader.assign` capability exists and is granted to `Admin` + `Staff` role policy only | `role_capabilities` rows: Admin + Staff have it, Member does not (seed policy + `hasCapability` query) |
| AUTH-2 | Program-leader grants (scoped) never imply `program.leader.assign` | `D1CapabilityAuthorizer.can` with leadership scope returns false for `PROGRAM_LEADER_ASSIGN`; true for `PROGRAM_MANAGE` (operational set kept) |
| AUTH-3 | Program Leader remains fully operational on their own program (no regression from PRG-01/02) | leader on P can `POST /schedule-rules`, `POST /events`, `POST /enrollments` on P → `201` each |

## 5. Audit contract

| # | Criterion | Assertion method |
| --- | --- | --- |
| AUD-1 | Every assignment/revocation appends an immutable audit row | `PROGRAM_LEADER_GRANT`/`PROGRAM_LEADER_REVOKE` rows with `actor_user_id`, `entity_id`, `new_value_json`, `correlation_id`; DELETE/UPDATE on the row → rejected |
| AUD-2 | No password, hash, token, or other credential material enters audit records | assert every `new_value_json`/`old_value_json` for leader actions contains only `user_id`/`program_id`/timestamps — no `password`, `hash`, `token`, `credential`, `secret` keys or values |

## 8. Verification status

**Implemented + verified 2026-08-06.** Branch `prg-04-200` (base `prg-03-199`).

Contract suite (`web/lib/programs/programs.test.ts`, `describe("PRG-04: program leaders")`, 22 tests) covers: AUTH-1 (capability is Admin/Staff only), DLG-1..DLG-18, AUTH-2 (leadership never implies `leader.assign`), AUTH-3 (leader operational on own program), AUD-2 (no credential material in leader audit JSON). Component suite (`programs-leaders-panel.test.tsx`, 5 tests) covers UI-1..UI-5.

Deviations from plan (recorded, behavior is intentional):
- DLG-11 asserts 403 on a revoked leader's schedule-rules POST only after making the fixture programs `Listed`; with `Unlisted` the handler 404s at `getProgram` (revoked leaders lose `PROGRAM_MANAGE` visibility too). Kept `Listed` so the test exercises the authorization path, not the visibility path.
- DLG-12 target changed to `U001` (never assigned): "already revoked" is a 200 no-op by design, so the 404 path is only reachable for never-assigned users.
- DLG-18 asserts 404 (masked "Unknown program.") for denied listing — `handleListProgramLeaders` deliberately hides program existence from non-managers (anti-enumeration), matching the assign/revoke asymmetry where capability-gated writes return 403.
- Test fixtures share one D1 database across suites; PRG-04 tests run last and must account for earlier tests leaving `U002`/`U003` as active leaders (DLG-18 tears U002 down first).
