# PRG-03 (#199) — EnrollmentRequest & Enrollment vertical slice

Status: Proposed → (verified below)
Parent: Spec #187, decision #184. Blocked by PRG-02 (#198, shipped).
Authored before implementation per ADR-0012 (headless gate).

## Scope

Complete Enrollment slice on the D1 Program system: Member requests on
`MemberRequest` programs, audited manager decisions, assisted direct-active
enrollment on `ManagerOnly` programs (no fake request), self/manager
cancellation that never reopens a record, and at most one Active
member–program relationship under concurrency.

Schema already shipped in migration `0002_d1_program_domain.sql` §8
(`enrollment_requests`, `enrollments`, partial unique index
`enrollments_active_member_program_idx`, `program_leaders`). **No new
migration.** Research #189 remains OPEN — no vocabulary changes; request
history keeps the schema's decision statuses.

## New capability

`program.enroll` (`PROGRAM_ENROLL`) granted to the Member role in
`DEFAULT_ROLE_POLICIES` (capabilities.ts). Managers keep `PROGRAM_MANAGE`
for decisions/assisted/cancel-others; members act only on their own records.

## Acceptance criteria (assertion method)

### Requests (REQ)

- REQ-1 `EnrollmentRequest` and `Enrollment` are separate rows; request
  history preserves Pending/Approved/Rejected/Withdrawn (worker contract:
  row assertions + status transitions).
- REQ-2 Submit on `MemberRequest` → 201 Pending; on `ManagerOnly` → 422;
  unknown program → 404; non-member actor → 403 (Staff has no
  `program.enroll`).
- REQ-3 Duplicate Pending request or existing Active enrollment → 409
  (worker contract; audit CONFLICT row).
- REQ-4 Approve → request Approved + Active Enrollment created with
  `request_id`, decided_by/decided_at set; audit `ENROLLMENT_REQUEST_DECIDE`
  (old/new snapshots) + `ENROLLMENT_CREATE`.
- REQ-5 Reject → request Rejected, no enrollment row.
- REQ-6 Withdraw own Pending → Withdrawn; withdraw after decision → 409;
  member cannot withdraw another member's request → 403.
- REQ-7 Decision race: two concurrent decisions → one succeeds, other 409;
  exactly one enrollment row (guarded UPDATE `WHERE status='Pending'`).

### Enrollments (ENR)

- ENR-1 Assisted enroll on `ManagerOnly` → Active enrollment with
  `request_id = NULL`, **no** request row (no fake request); on
  `MemberRequest` → 422.
- ENR-2 Assisted enroll for unknown member_user_id → 422 (validated via
  accounts table, not FK 500).
- ENR-3 Concurrency: partial unique index + guarded inserts → at most one
  Active member–program row (two parallel assisted enrolls → one 201, one
  409).
- ENR-4 Member cancels own Active → Cancelled + cancelled_at/by set; manager
  cancels any in scope → same; member cancels another's → 403.
- ENR-5 Cancellation never reopens (second cancel → 409); re-enrollment
  creates a **new** enrollment_id; old row stays Cancelled.
- ENR-6 Member list shows own rows only; manager list shows all; Unlisted
  program invisible to members (404 path via `getProgram`).
- ENR-7 Audit rows exist for CREATE/DECIDE/WITHDRAW/CREATE/CANCEL with
  correlation_id = requestId and SUCCESS outcomes.
- ENR-8 No credential material in any enrollment response body.

### UI (UI)

- UI-1 Member on `MemberRequest`: request button; own request list
  (Pending + withdraw); after approve: Active enrollment + cancel.
- UI-2 Member on `ManagerOnly`: read-only "managed enrollment" note, no
  request affordance.
- UI-3 Manager queue: Pending requests with approve/reject; status flips on
  decision.
- UI-4 Manager assisted form (member id input) on `ManagerOnly`; success
  lists the new Active enrollment.
- UI-5 Cancel paths (own + manager) show notice and refreshed status.
- UI-6 Errors (409 duplicate, 422) surface mapped copy in `role="alert"`;
  no credential material in fixtures.
