# AUTH-01 (#255) — Department Manager scoped authority — acceptance trace

> This trace is written **before** implementation (ADR-0029 headless gate /
> AGENTS.md). Each acceptance criterion names the worker, database, or DOM
> assertion that proves it. Verification results are appended at the end.

Basis: ticket #255 acceptance criteria + ADR-0027 audit vocabulary. Authorization is always derived from server-provided effective capabilities; client role names are never an authorization input.

## 1. Program Leader relationship and delegation

| # | Criterion | Assertion method |
| --- | --- | --- |
| DLG-1 | Program Leader assignment and revocation remain under the selected Program Settings surface and are scoped to one Program | Program Workspace Settings renders the Leaders panel only for effective `program.manage`/`program.leader.assign`; API routes include the exact `program_id` and relationship state |
| DLG-2 | Only active eligible accounts can be delegated; self-delegation is denied | Member search returns active eligible accounts; self-grant returns `403` and exactly one `DENIED` audit row |
| DLG-3 | Duplicate, repeated revoke, and concurrent relationship changes have deterministic outcomes | Existing active/revoked row paths return explicit `DUPLICATE`/terminal state; concurrent grants of a brand-new pair collapse to one active row with one `SUCCESS` and one `CONFLICT` audit; the store INSERT is conflict-guarded so the losing request never 500s; store failures audit `FAILED` before propagating |

## 2. Department Manager scope and inheritance

| # | Criterion | Assertion method |
| --- | --- | --- |
| AUTH-1 | Department Manager is a scoped relationship, not a global role | `department_managers(department_id,user_id)` stores grant/revoke history; no `program_leaders` rows are created when a Department Manager is assigned |
| AUTH-2 | Assignment grants current and future Program capabilities only inside assigned Departments | Authorizer checks active Department Manager rows for `department.manage`, `department.publish`, `department.module_configure`, `program.manage`, `program.publish`, and exact-Program `program.leader.assign`; tests cover current Program, newly created Program, and unrelated Department denial |
| AUTH-3 | Department Manager cannot assign Department Managers, edit global roles, or widen scope | Capability matrix omits `department.manager.assign` from inherited manager capabilities; manager self-grant, cross-scope grant, and Program Leader grant attempts return `403` with `DENIED` audit state |
| AUTH-4 | Only active eligible accounts may be assigned; revoked assignments immediately lose inherited access | Inactive target assignment returns `422` with no active row and `FAILED` audit; revoke preserves history and authorizer returns false afterwards |
| AUTH-5 | Department Manager can use approved Department operations inside scope only | Department details, module composition, Program creation, and Program Leader delegation are capability-gated by the assigned Department; cross-Department requests are masked or denied without leakage |

## 3. Safe reads and audit contract

| # | Criterion | Assertion method |
| --- | --- | --- |
| SAFE-1 | Protected reads independently reauthorize server-side and project safe DTOs | Department and manager handlers return only capability-appropriate fields; sensitive `created_by`, `updated_by`, `enabled_by`, and credential material are not sent to the browser; manager-only read has no module details without `department.module_configure` |
| AUD-1 | Every terminal Department Manager grant/revoke appends exactly one immutable audit outcome, including store failures | Integration tests inspect `DEPARTMENT_MANAGER_GRANT`/`DEPARTMENT_MANAGER_REVOKE` rows for `SUCCESS`, `DUPLICATE`, `CONFLICT`, `DENIED`, and `FAILED` outcomes; a throwing store adapter yields a `FAILED` audit and a propagated error |
| AUD-2 | Audit payloads contain relationship identifiers only | Assertions reject password, hash, token, credential, secret, or unrelated account fields in grant/revoke audit JSON |

### Review-driven fixes landed in the implementation commit (all covered by the gates above)

- **Raw `program_leaders` INSERT race** → `ON CONFLICT(program_id, user_id) DO NOTHING` + `AND revoked_at IS NOT NULL` reactivation guard (mirrors the manager store method); the losing concurrent grant reaches the domain post-read and audits `CONFLICT` instead of crashing with an uncaught UNIQUE exception.
- **Store-failure audit gap** → grant/revoke store calls for both relationship types catch D1 exceptions, write a `FAILED` audit row (`reason: "store_error"`), then rethrow.
- **Focus management** → expanding Department settings moves focus to the panel landing node; collapsing returns focus to the launcher trigger (component test + live browser verification).
- **Lint hygiene** → `validation`/`notFound` helpers hoisted above route handlers in `program-handlers.ts` (also clears two pre-existing no-use-before-define flags), `assignDepartmentManager` if/else collapsed to a ternary, launcher uses `querySelector`, test store uses an instance field.
