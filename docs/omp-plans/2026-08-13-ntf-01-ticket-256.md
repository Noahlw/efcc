## Design decision: the two attention sources

The issue requires counts "derived from current authorized Event/Enrollment queues" without fabricating a feed. Two real, already-durable, capability-scoped server queries satisfy this without new schema:

1. **Enrollment**: Pending enrollment requests per program (`enrollment_requests` where `status = 'Pending'`), authorized via the exact scope resolution `listEnrollmentRequests` (#253) already uses (manager sees every row in scope; module-gated).
2. **Event**: Incomplete recurring-generation runs per program (`program_generation_runs` where `status IN ('partial', 'failed')`, #252), authorized via the exact scope resolution `listManagementDirectory`/`generateEvents` already use (module-gated on `events`). #252's `finishGenerationRun` fix (this session) makes retrying such a run now durably re-settle, so surfacing "this program has an incomplete generation, retry it" is an honest, actionable, now-safe-to-act-on signal.

No other Event/Enrollment state qualifies: cancelled/deactivated Events carry no "needs resolution" flag anywhere in the schema (`cancel_reason` is just stored text), so a third "cancellation" attention source would be fabricated and is deliberately excluded. AC4's "availability correction, cancellation resolution" language is read as mutation **triggers** that must refresh the two counts above (e.g. resolving a stale/blocked deactivation lets an operator move on to their next queue item), not as a third counted source.

## Observable setup

1. Start the local app with `pnpm dev:local`.
2. Seed the disposable fixtures with the checked-in local seed commands.
3. As a scoped Manager/Leader with Program Manage capability, submit at least one Pending enrollment request (via a participant fixture) and leave at least one Recurring program's generation run partial/failed (e.g. via a stale-plan or a seeded failed item), then open Management.

## Acceptance criteria

### NTF-01.1 — Bounded actionable counts at both entry points

- The Management Directory landing shows a per-program actionable badge (Pending enrollment count + incomplete-generation count) sourced from a single authorized aggregate read, not client-side derivation from full unscoped lists.
- The Program Workspace's Participants task (and Events task, for the generation signal) shows the same counts already computed for its own program, consistent with the Directory's badge for that program.
- A compact global notification control (bounded, not a persistent dashboard card) is reachable from the Management shell and shows the same totals capped to a small bounded list (e.g. top N items) with a "view all" fallback when more exist.

### NTF-01.2 — Deep links are exact and revalidated

- Every attention item (Directory badge, notification-control entry) deep-links via the existing `programs-intent.ts` URL contract directly to the owning Program's Participants task (Enrollment source) or Events task (Generation source).
- Opening a deep link re-authorizes and re-reads current object state; a request that is no longer Pending (already decided elsewhere), a generation run that already completed, or a program the actor lost access to resolves to the existing recoverable NOT_FOUND/FORBIDDEN/unavailable states already used by `ProgramWorkspace` and `EventDetail` — never a dead link or a stale-looking success.

### NTF-01.3 — Distinct informational, actionable, and zero states

- The notification control visually distinguishes "has actionable items" (non-zero count, opens the bounded list) from "zero" (no badge/dot, explicit zero-state copy on open, never hidden entirely) without introducing a third unread/informational category not backed by real state.
- No generic persistent "Needs Attention" card is added anywhere; badges only render adjacent to the real Program/task row they describe.

### NTF-01.4 — Counts update after the real triggers and stay capability-scoped

- After approving/rejecting a Pending request, the affected program's badge and the notification control total decrease without a manual page reload (reuse the existing post-mutation refresh path).
- After a successful (or resumed-to-completion) generation retry, the affected program's generation badge clears.
- After a Program Leader/Department Manager capability is revoked for the current actor, a subsequent load of the Directory/notification control no longer includes programs the actor can no longer manage — the server aggregate is always computed from current authorization, never cached client state.
- No push/email/SMS delivery, no polling loop, no persisted read/unread/notification-history table is introduced; every count is a fresh authorized read at load/refresh time.

### NTF-01.5 — Reachability and accessibility

- The notification control and every Directory badge have accessible names/roles, are keyboard-operable, and remain usable at narrow viewport widths.
- Loading, error, and zero states are visible in the DOM with accessible live-region announcements consistent with the rest of the Programs module's existing patterns.

## Required evidence

- Focused worker/store tests for the two aggregate queries' scope-authorization (manager sees only in-scope programs, module-gated, matches `listEnrollmentRequests`/`listManagementDirectory`'s existing tests) and count-accuracy after each AC4 trigger.
- Component tests for the Directory badges, the notification control's bounded list/zero-state/deep-links, and stale-item recovery.
- Local Playwright trace against `wrangler dev` + local D1, with each criterion asserted through DOM or response state.
- Evidence paths recorded in this file after verification; automated tests may reset only disposable `E2E_`/`E2E_DEMO_` fixtures.
