## Design decision: the two real base-available sources

The issue requires counts derived from current authorized Event/Enrollment queues without fabricating a feed. The live #256 base contains two durable sources:

1. **Enrollment**: Pending enrollment requests per program (`enrollment_requests` where `status = 'Pending'`), authorized through the exact `PROGRAM_MANAGE` plus enrollment-module gate used by `listEnrollmentRequests` (#253). A pending row is actionable and contributes to the per-program/actionable totals.
2. **Event operational state**: current upcoming Event rows (`starts_at >= now`) whose persisted state needs operator review: an Active Event with `availability = 'Inactive'` is actionable (availability correction), while a Cancelled Event is an explicit terminal informational record. Both use the exact management scope plus events-module gate used by `listEvents`/`getEventDetail` (#251), and each deep-links to the existing Events task/event detail.

The original trace named `program_generation_runs` from sibling #252, but that table and its retry workflow are not present on this branch. Porting #252 would silently widen the ticket's dependency and creates central-file merge conflicts, so this trace is corrected instead of inventing a generation source. Cancelled Events are not an unread/history feed: they are bounded operational-state notices. No third cancellation queue, push/email/SMS delivery, polling loop, or persisted notification history is introduced.

## Observable setup

1. Start the local app with `pnpm dev:local`.
2. Seed the disposable fixtures with the checked-in local seed commands.
3. As a scoped Manager/Leader with Program Manage capability, submit at least one Pending enrollment request (via a participant fixture), create or use an upcoming Event with `availability = 'Inactive'` (and optionally a current Cancelled Event), then open Management. No generation-run fixture is required because #252 is not on this branch.

## Acceptance criteria

### NTF-01.1 — Bounded actionable counts at both entry points
- The Management Directory landing shows a per-program badge with actionable pending-enrollment plus inactive-upcoming-Event counts, sourced from a single authorized aggregate read, not client-side derivation from full unscoped lists. Cancelled Event notices may appear in the bounded notification list but are explicitly informational and do not inflate the actionable badge.
- The Program Workspace's Participants task shows the pending-enrollment count and its Events task shows the inactive operational count (plus any bounded informational cancelled-state notice) computed for its own program, consistent with the Directory badge for that program.
- A compact global notification control (bounded, not a persistent dashboard card) is reachable from the Management shell and shows the same actionable totals capped to a small bounded list (e.g. top N items), with a "view all" fallback when more items exist.

### NTF-01.2 — Deep links are exact and revalidated
- Every enrollment attention item deep-links via the existing `programs-intent.ts` URL contract directly to the owning Program's Participants task. Every Event operational item deep-links to the owning Program's Events task and, where an event identity is available, the exact Event detail (`event=<id>`).
- Opening a deep link re-authorizes and re-reads current object state; a request that is no longer Pending, an Event whose availability/cancellation state has changed, or a program/event the actor lost access to resolves to the existing recoverable NOT_FOUND/FORBIDDEN/unavailable states already used by `ProgramWorkspace` and `EventDetail` — never a dead link or a stale-looking success.

### NTF-01.3 — Distinct informational, actionable, and zero states

- The notification control visually distinguishes "has actionable items" (non-zero count, opens the bounded list) from "zero" (no badge/dot, explicit zero-state copy on open, never hidden entirely) without introducing a third unread/informational category not backed by real state.
- No generic persistent "Needs Attention" card is added anywhere; badges only render adjacent to the real Program/task row they describe.

### NTF-01.4 — Counts update after real triggers and stay capability-scoped
- After approving/rejecting a Pending request, the affected program's pending badge and notification-control actionable total decrease without a manual page reload (reuse the existing post-mutation refresh path).
- After correcting an inactive Event availability, the affected program's Event/actionable badge clears; after cancellation, the Event operational notice appears or changes in the fresh aggregate rather than being treated as an unread mutation history.
- After a Program Leader/Department Manager capability is revoked for the current actor, a subsequent load of the Directory/notification control no longer includes programs the actor can no longer manage — the server aggregate is always computed from current authorization, never cached client state.
- No push/email/SMS delivery, no polling loop, no persisted read/unread/notification-history table is introduced; every count is a fresh authorized read at load/refresh time.

### NTF-01.5 — Reachability and accessibility

- The notification control and every Directory badge have accessible names/roles, are keyboard-operable, and remain usable at narrow viewport widths.
- Loading, error, and zero states are visible in the DOM with accessible live-region announcements consistent with the rest of the Programs module's existing patterns.

## Required evidence
- Focused worker/store tests for the two aggregate queries' scope-authorization (manager sees only in-scope programs, module-gated, matches `listEnrollmentRequests`/`listEvents`' existing tests) and count-accuracy after approval/rejection and Event availability/cancellation mutations.
- Component tests for the Directory badges, the notification control's bounded list/zero-state/deep-links, and stale-item recovery.
- Local Playwright trace against `wrangler dev` + local D1, with each criterion asserted through DOM or response state.
- Evidence paths recorded in this file after verification; automated tests may reset only disposable `E2E_`/`E2E_DEMO_` fixtures.
