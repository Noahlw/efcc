## 0. Environment model

One Cloudflare Worker origin (`web/wrangler.jsonc`, `efcc-prototype-129`) hosts:
- the Next.js static export via the `ASSETS` binding (`web/worker.ts` line 22: non-`/api` falls through to ASSETS);
- the cookie-only `/api/v1/auth/*` and `/api/v1/programs/*` surfaces backed by D1 (`DB` binding, migrations `web/migrations/`);
- a rate-limiter binding (session-keyed, no `E2E_`-relevant limits).

Deployed gate precedent: `.github/workflows/e2e.yml` `deployed-auth` job — `workflow_dispatch` only, fail-closed prereqs, reserved `efcc-auth-*.efcc-ggc.workers.dev` acceptance hostname (`.github/CI-SECRETS.md`). PRG-05 follows the same operator rotation flow (deploy branch worker → apply D1 migrations → seed acceptance accounts → set repo vars/secrets → dispatch) and adds the Programs surface to it.

The browser UI is a client of server-authoritative capabilities: every protected action is enforced in the Worker (`D1CapabilityAuthorizer`, `LEADERSHIP_CAPABILITIES` allow-list from PRG-04), and the suite asserts server responses, never client-side gating alone.

## 2. Deployed suite design (`tests/e2e/programs-d1.config.ts` + `programs-d1.test.ts`)

- **Prereqs (secrets)**: `PROGRAMS_ADMIN_USERNAME`/`PROGRAMS_ADMIN_CREDENTIAL`, `PROGRAMS_STAFF_USERNAME`/`PROGRAMS_STAFF_CREDENTIAL`, `PROGRAMS_MEMBER_USERNAME`/`PROGRAMS_MEMBER_CREDENTIAL` — three operator-seeded accounts, all `E2E_`-prefixed (disposable convention, same as `auth-d1`).
- **Var**: `PROGRAMS_TARGET_URL` — HTTPS URL on the reserved `efcc-auth-*.efcc-ggc.workers.dev` acceptance hostname. Config fails closed on missing var, non-HTTPS, embedded credentials, or off-hostname. Local deterministic runs (agent/CI precheck) opt into `PROGRAMS_ALLOW_LOCAL=1` for `http://localhost:*` only — never permitted in CI (the env var is absent there).
- **Login**: real UI login (`page.goto(baseURL)` → login form on `/` → submit → cookie set), then `page.goto("/programs")` (E2E-01, E2E-02, E2E-03 run per role).
- **Isolation**: every run creates `E2E_<runId>`-prefixed department/program/rule/leader rows so repeated dispatches are idempotent; no cleanup needed (disposable target DB).
- **Projects**: `phone` = Pixel 5 (393×851, `isMobile: true`), `desktop` = Desktop Chrome (1280×720).
- **Transport**: `trace: "off"` (request bodies carry credentials); reporters `list` + `json` artifact.

### Test-suite deviations from the trace (recorded, intentional)

The trace's E2E-08/09/10/11 used **staff** as the program leader. In the implemented UI, `canManage` is `role === "Admin" || "Staff"` only (`web/lib/programs/programs-manager.tsx:57`) — staff already holds `PROGRAM_*` globally, so staff-as-leader cannot isolate the leadership grant. Corrected to use the **member** as leader (only `PROGRAM_ENROLL` globally; manage arrives solely via the `program_leaders` grant):

- E2E-08 now proves the member-leader gains server-side manage: member-leader POST schedule-rules → 201 (grant effective), and the leader row persists on reload.
- E2E-09 member-leader assign another leader → 403 (delegation is `PROGRAM_LEADER_ASSIGN`, Admin/Staff only; not in `LEADERSHIP_CAPABILITIES`).
- E2E-10 revoked member-leader loses manage: POST schedule-rules → 403.
- E2E-11 member-leader GET own program leaders → 200; cross-program → 404 (mask).

These are the server-authoritative proofs the capability model requires; the post-edit hook/DOM assertions were adjusted to match.
