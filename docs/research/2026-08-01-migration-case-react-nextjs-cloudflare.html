Why switch at all?

Today the app is a vanilla Google Apps Script HtmlService web app. It works — but three hard platform limits are now blocking the next phase of the church system. Cloudflare removes all three.

Reason 1 · The scanner is boxed in

The #1 driver. Google hard-blocks the camera inside the Apps Script iframe — getUserMedia() throws a Permissions-Policy violation. Today we're forced to pop open a separate scanner tab. On Cloudflare (a normal web origin) the camera runs inline, on one page, with continuous scanning — exactly the check-in UX we want.

Source: Google Apps Script Troubleshooting (official); ADR-0015.
Reason 2 · The 5 MB ceiling is gone

Apps Script caps each project at ~5 MB. It already forced us to retire React once (ADR-0007). On Cloudflare, assets are served as normal static files — no ceiling, no inlining, room for every future feature.

Source: ADR-0007 (5 MB GAS project limit).
Reason 3 · Faster feature delivery

Half the system isn't built yet — Events, Care dashboard, Permissions, registration, event & enrollment management. A modern component framework (React + TypeScript) ships these faster and more safely than hand-rolled vanilla JS across a 2,600-line controller.

Source: CONTEXT.md (section build status); src/gas/shell-session.js.html.
Reason 4 · A real SaaS growth path

The roadmap goes beyond attendance: giving/payments, a member portal, events, communication. These need a real frontend — not an Apps Script iframe. Migrating now is the foundation, not a detour.

Source: Migration scope analysis (2026-08-01).

The honest cons — and how we handle them

We're not hiding the tradeoffs. Each has a clear mitigation.

Toolchain burden on volunteers

ADR-0007's surviving concern. Mitigation: thorough docs, the backend stays in familiar Apps Script, and a new ADR records why the 5 MB + camera reasons now outweigh it.

A CORS proxy is required

Apps Script can't emit CORS headers, so a small Cloudflare proxy fronts the API. Mitigation: it's free, documented, tested, and counted in the 1.18% above.

Migration effort

~27–41 volunteer-days for feature parity. Mitigation: phased into 7 milestones / 22 tracked issues; backend logic is reused, not rewritten.

Two deploy systems

Cloudflare (frontend) + clasp (backend). Mitigation: separate repo per side, each with its own fitting CI.

The bottom line

We switch because Apps Script structurally cannot run the camera inline and caps the project at 5 MB — both blocking the scanner UX and the SaaS roadmap. Cloudflare removes both, costs the same $0/month, and stays inside the free tier with 84× headroom on our busiest day. The tradeoff is a one-time ~27–41 day migration and a CORS proxy — a price worth paying to unblock the church system's next phase.
