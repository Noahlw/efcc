# Research Output — #87 Camera APIs in deployed Apps Script HTML Service

## Recommendation (plain)

**Do not plan F5 Scanner camera inside the stable HtmlService App Document.** Official Apps Script docs and the live `/exec` IFRAME both show camera access is blocked by Permissions Policy. Follow Google’s documented workaround: host camera capture on a **separate HTTPS origin**, open it via `window.open` (user gesture), return only the decoded opaque string (or capture metadata) with **`postMessage`**, verifying `event.origin`. App Document / Scanner Section still owns entry/exit UX and must close the window and drop listeners on unmount — but **tracks live outside the sandbox**.

**Prototype required:** external-host spike on representative iPhone Safari + Android Chrome (permission grant/deny/retry, backgrounding, front/rear, repeated Scanner entry). Prototype is **not** to prove in-iframe `getUserMedia` — that path is already falsified for Day 1 architecture.

## Supported behavior / constraints

| Topic | Finding | Source |
| --- | --- | --- |
| HtmlService + `getUserMedia` | Apps Script documents a **Permissions policy violation** when HtmlService tries sensitive APIs such as `navigator.mediaDevices.getUserMedia()` for camera/microphone. Sandbox “restricts these features.” | [Troubleshooting — Permissions policy violation](https://developers.google.com/apps-script/guides/support/troubleshooting) (Context7 + direct fetch 2026-07-30) |
| Official workaround | Host permission-requiring work on a **separate domain**, open in a new window/tab, return data via `postMessage` (with `event.origin` check). | Same troubleshooting page + sample |
| IFRAME sandbox keywords | Documented sandbox tokens: `allow-same-origin`, `allow-forms`, `allow-scripts`, `allow-popups`, `allow-downloads`, `allow-modals`, `allow-popups-to-escape-sandbox`, `allow-top-navigation-by-user-activation`. **No camera / Permissions-Policy grant documented.** | [HTML Service: Restrictions](https://developers.google.com/apps-script/guides/html/restrictions) |
| HTTPS active content | External scripts/styles/XHR must be HTTPS in IFRAME mode. | Same restrictions page |
| Browser: secure context | `getUserMedia` requires a secure context; insecure → `navigator.mediaDevices` undefined / TypeError. | [MDN MediaDevices.getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia) |
| Browser: iframe + Permissions Policy | Nested documents need the embedding frame to grant `camera` (e.g. `allow="camera"`). Default policy for `camera` is `self`. Without grant, `getUserMedia` rejects with `NotAllowedError`. | [MDN getUserMedia — Permissions Policy](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia); [Permissions-Policy: camera](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Permissions-Policy/camera) |
| Front / rear | Prefer `video: { facingMode: "environment" }` for rear; `"user"` for front; may need to `track.stop()` before switching. | MDN getUserMedia examples |
| Track stop | Call `MediaStreamTrack.stop()` on each track to release the device. | Media Capture and Streams / MDN |

## Deployed `/exec` observations (2026-07-30)

**Target:** CI variable `E2E_TARGET_URL` =  
`https://script.google.com/macros/s/AKfycbyJYzeQE_YJik1JCTEq_KlXFn2CrAdRM-CMc1CgaugzWwhLuIsGHlAw-8Q5dP6qgTm2/exec`  
(also cited in prior deployment research / form-protection plan). Cold-start Playwright Chromium — **no EFCC PIN login** (camera policy is structural).

### Outer `#sandboxFrame` attributes (top-level `/exec` document)

- **`allow`:** includes accelerometer, autoplay, clipboard-*, encrypted-media, fullscreen, geolocation, gyroscope, local-network-access, magnetometer, midi, payment, picture-in-picture, screen-wake-lock, sync-xhr, web-share — **`camera` and `microphone` are absent** (`allowHasCamera: false`).
- **`sandbox`:** includes `allow-popups` and `allow-popups-to-escape-sandbox` (supports the documented external-window pattern), plus `allow-same-origin`, `allow-scripts`, forms, modals, downloads, top-navigation-by-user-activation, storage-access-by-user-activation.

### Inside `userCodeAppPanel` (developer HtmlService document)

| Check | Result |
| --- | --- |
| `window.isSecureContext` | `true` |
| `navigator.mediaDevices` present | `true` |
| `document.featurePolicy.allowsFeature("camera")` | **`false`** |
| `allowsFeature("microphone")` | **`false`** |
| `getUserMedia({ video: { facingMode: "environment" } })` | Rejects; console: **`Permissions policy violation: camera is not allowed in this document.`** (Playwright also surfaced `NotSupportedError` / “Not supported” in headless — treat console Permissions-policy error + missing `allow=camera` as authoritative) |
| `#app` / `data-app-state` | Present / `SIGNED_OUT` on successful frame resolve |

**Interpretation:** Even though the page is HTTPS and `mediaDevices` exists, the **Google-controlled embed does not delegate camera** to the Apps Script user document. This matches official troubleshooting. Product code cannot fix this from inside `doGet()` HTML — developers do not control the outer iframe’s `allow` list ([PWA research](docs/research/2026-07-30-apps-script-pwa-home-screen.md) architecture: outer chrome is Google’s).

**Implication for ADR-0010:** “QR scanner library … once per App Document” assumed in-document camera/decode. That assumption is **invalid for camera**. Section mount/unmount remains correct for **UI + popup/listener lifecycle**; camera/decode move off-document.

# Research Output — #88 QR decoding library and dependency strategy

## Recommendation (plain)

**Decode on the external camera origin established by #87. Do not load `html5-qrcode` (or any camera-bound scanner) into the HtmlService App Document.**

1. **Primary (historical continuity):** On the external HTTPS page, use pinned **`html5-qrcode@2.3.8`** (matches [spec 009](docs/specs/009-phone-first-shell-navigation.md) pin). It already prefers `BarcodeDetector` when supported and falls back to its bundled decoder ([v2.3.4 release notes](https://github.com/mebjas/html5-qrcode/releases)).
2. **Credible alternative:** External page owns `getUserMedia` + canvas/`ImageData` + **`jsQR`** (camera-agnostic; Apache-2.0; npm `jsqr`). Better if EFCC wants full ownership of mount/unmount without library viewport CSS (historical risk called out in #34).
3. **App Document:** Once-per-document listener module only — open external scanner URL with user gesture, accept `postMessage` opaque string, tear down on Section `unmount`. **No CDN camera library inside GAS HTML** (avoids ADR-0007 size pressure and useless in-sandbox load).
4. **Reject as sole strategy:** Native **`BarcodeDetector` only** — Safari / iOS still not usable for a phone-first church app ([Can I Use](https://caniuse.com/mdn-api_barcodedetector): Safari/iOS “Disabled by default”; Firefox unsupported).

## Comparison

| Approach | Browser coverage | Loading / CSP | Maintenance | Cleanup / repeated frames | Fits #87 external lifecycle? |
| --- | --- | --- | --- | --- | --- |
| **`BarcodeDetector` only** | Chrome/Edge/Android partial; **Safari/iOS no** | None (built-in) | Browser-owned | App owns rAF loop + cooldown (#91) | Yes on Chromium external host only — **insufficient alone** |
| **`html5-qrcode@2.3.8`** | Broad; wraps camera + decode; optional BarcodeDetector | HTTPS script on **external** origin; pin version | Last npm release **2023-04-15** (stale but high download volume); Apache-2.0 | Library `stop`/`clear`; FPS config; cooldown still #91 | **Yes — place on external host** |
| **`getUserMedia` + `jsQR`** | Wherever camera works | Small pure JS on external origin; HTTPS | `jsqr@1.4.0` (API stable; package metadata refreshed 2025) | Full app ownership of tracks + decode cadence | **Yes — best lifecycle control** |
| **Clasp-include decoder into GAS** | N/A for camera (still blocked) | Inflates project toward **5 MB** ceiling ([ADR-0007](docs/adr/0007-vanilla-multipage-html-service.md)) | — | — | **Rejected** for camera path; optional only if someday decoding static images inside GAS (not Day 1) |
| **In-document CDN `html5-qrcode`** (spec 009 historical) | Would still call `getUserMedia` in sandbox | HTTPS OK per restrictions, but **camera policy fails** | — | — | **Rejected** given #87 |

## Dependency / loading strategy

| Layer | Strategy |
| --- | --- |
| External scanner page | Static HTTPS hosting under an origin EFCC controls. Load pinned decoder via HTTPS `<script>` or self-host the file (preferred for supply-chain). |
| Message contract | `postMessage` payload: `{ type: "EFCC_QR_SCAN", scannedCode: "<opaque>" }` (name TBD in focused spec). **No Member DTO, no authority.** Parent verifies `event.origin`. |
| App Document | Register `message` listener in Scanner `mount`; remove in `unmount`; close child window. Aligns with #51 “Leaving Scanner stops the camera…” at the **ownership** level (window + listener), even though tracks are off-document. |
| ADR-0010 asset loader | **Repurpose or narrow:** once-per-document loader may still load a tiny **bridge** script, not a multi-hundred-KB scanner. Update ADR when camera ownership is recorded. |
| HtmlService CSP/HTTPS | External active content must be HTTPS ([Restrictions](https://developers.google.com/apps-script/guides/html/restrictions)). External page’s own CSP is under EFCC control. |

## Rejected alternatives (summary)

- **In-sandbox `html5-qrcode` / any in-iframe camera library** — #87 falsifies.
- **BarcodeDetector-only** — no Safari/iOS production path.
- **Bundling large scanner into clasp project** — ADR-0007 size lesson; does not unlock camera.
- **Server-side decode of uploaded frames** — out of scope, latency/privacy worse, still needs camera capture client-side.

## Risks

| Risk | Mitigation |
| --- | --- |
| `html5-qrcode` maintenance stall since 2023 | Pin exact file hash/self-host; keep `jsQR` escape hatch |
| External host availability / CDN outage | Self-host assets; Scanner shows recoverable error + F6 manual path |
| Popup blockers | Open only from user gesture; clear copy |
| Library-owned viewport CSS (#34) | Prefer `jsQR` + EFCC UI, or carefully configure `html5-qrcode` without full scanner widget |
| Double-deciding cooldown | Library FPS ≠ product cooldown — leave quiet-success / chime rules to **#91** / #51 |
| Origin spoofing | Strict `event.origin` allowlist; never trust message without it |

# Research Output — #89 Existing EFCC member QR payload and compatibility

## Recommendation / disposition

**Day 1 Scanner must treat the encoded value as the member check-in identifier `QR_Code_String`, shape `GC-XXXX-XXXX`, equal to `User_ID` by convention, stable and non-secret.** Grill [#90](https://github.com/Noahlw/efcc/issues/90) already resolved the trust contract from these inputs; this ticket supplies the sanitized inventory and compatibility matrix. **Live sheet distribution counts are still UNKNOWN** (xlsx not in repo; agents must not mutate Sheets) — treat as operator follow-up / compatibility amendment if divergence appears, **not** a reopen of secret/rotating-token design.

## Sanitized payload inventory

| Shape / pattern | Where it appears | Notes |
| --- | --- | --- |
| `GC-XXXX-XXXX` (two hex segments) | ADR-0013 User_ID; spec 001; spec 006 example `GC-A1B2-C3D4`; CONTEXT glossary; login fixture uses same string for User_ID and QR cells | Canonical Day 1 member id / QR payload |
| `QR_Code_String` column | Users sheet col 9 (ADR-0013); “Typically same as User_ID”; required | Sheet field scanned conceptually |
| Empty `QR_Code_String` | CONTEXT: “defaults to User_ID when empty”; `usersRowToDto_` maps empty → `""` (no substitute at map time) | #90 resolve rule: match `QR_Code_String === scanned` **or** (empty QR **and** `User_ID === scanned`) |
| Profile pass rendering | `shell-session.js.html` builds `https://api.qrserver.com/v1/create-qr-code/?…&data=` + `encodeURIComponent(qrCodeString)` | Whatever is in `session/profile.qrCodeString` is what the on-screen pass encodes today |
| Historical RPC name `qrOrUserId` | spec 006 | Superseded naming; #90 uses `scannedCode` |
| Test-only `QR-U001` / `QR-${id}` | Several unit fixtures | **Not** production shapes — do not treat as live inventory |

**No real member secrets/identifiers** are published here.
