# Public Guest Check-In Entry

**Status:** Proposed

The signed-out login surface exposes a secondary **Guest Check-In** action that opens a public attendance flow without creating a Session; Program Check-In QR deep links may enter the same flow directly. A visitor or authenticated account holder may explicitly choose Guest Check-In. Guests provide a required phone and name, with Hong Kong local and `+852` forms normalized to one duplicate key; one active guest attendance is allowed per normalized phone and Event. Public writes use rate limiting and duplicate guards rather than OTP. Guest name and phone remain attached to attendance history under role-scoped access; Admin/Staff or the active Program Leader for the Event's Program may correct those fields in place with old/new values and a reason. A duplicate public submission shows only a neutral notice and directs the visitor to the Event Leader; it never reveals the existing guest's name or time. Voiding a guest row releases its duplicate slot for a later check-in. An authenticated guest-mode submission retains `checked_in_by` and audit attribution while leaving `member_user_id` NULL. If a guest later signs in, the Event token is preserved and revalidated before Self Check-In, but guest and member attendance records are never automatically merged. The permanent Program QR may be printed as the venue marker; the changing Event Manual Code is shown digitally or on a fresh downloadable/printable Event Check-In Sheet generated by Program/Event managers. When multiple Events have open windows, the permanent Program QR presents only those open Events by name and time for explicit selection. Cancellation invalidates the Event's QR/manual-code check-in immediately; rescheduling the same Event preserves its never-reused manual code and moves the check-in window only before attendance exists; after attendance, a new Event is required. This avoids forced registration and placeholder guest accounts, but requires a protected public write boundary and nullable member identity on guest attendance records.

**Considered Options:** Force login/registration before attendance; rejected because it blocks visitors at the venue. Create placeholder guest accounts; rejected because it pollutes the identity authority with non-accounts.
